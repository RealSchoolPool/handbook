# Домашнее задание №5 — «Решает, но не печатает»

**Срок:** к занятию в пятницу 25.09, 11:00.
**Время:** 30–40 минут.
**Сдавать:** файлы `.py` — в репозиторий команды, если уже получается; если нет — в чат
или принести завтра. Текст для шага 4 — `.md`.

> Сегодня вы написали первый код бизнес-логики — `core`: функцию, которая **решает**, что
> нужно пользователю, и **ничего не печатает**. Печатает отдельная часть программы.
> Это ДЗ — о том, зачем их разделили: теперь решение можно проверить, не запуская
> программу целиком.
>
> Поездка к заказчику в другую школу перенесена на понедельник. Это не потеря, а подарок:
> в понедельник вы покажете не рассказ о программе, а работающую программу.

## Правило, ради которого всё это

> **`core` ничего не печатает. `cli` ничего не решает.**

```text
   данные ──► core.py ──► список ответов ──► cli.py ──► print
                 │
                 └── здесь нет ни одного print и ни одного input
```

Подробнее — в [ARCHITECTURE.md](ARCHITECTURE.md#3-правило-на-котором-всё-держится).

## Шаг 1. Довести `core.py`

В `core.py` — функция, которая получает список и **возвращает** список нужного:

```python
def filter_items(items):
    result = []
    for ... in items:
        if ...:
            result.append(...)
    return result
```

Имя функции и условие — ваши, из вопроса в первой строке `project.py` (ДЗ №4).

Проверьте себя:

- в `core.py` нет ни одного `print` и ни одного `input`;
- функция заканчивается на `return`, а не на печати.

Если на занятии не успели — сделайте это из своего `project.py`: цикл и `if` переезжают
в функцию, `print` остаётся снаружи.

## Шаг 2. `cli.py` печатает то, что решил `core`

```python
from core import filter_items

items = [
    # ... ваши строки из project.py
]

for line in filter_items(items):
    print(line)
```

```
python cli.py
```

Должно напечататься **ровно то же, что печатал `project.py`**. Снаружи ничего не изменилось —
поменялось устройство внутри. Это и называется рефакторингом.

## Шаг 3. Первая проверка без запуска программы

Ради этого шага и нужно было разделение. Создайте `check_core.py`:

```python
from core import filter_items

items = [
    # 3–4 строки из ваших данных, не больше
]

expected = [
    # что функция должна вернуть — выписать ДО запуска
]

print(filter_items(items) == expected)
```

```
python check_core.py
```

1. Напечаталось `True` — функция решает правильно.
2. **Теперь сломайте нарочно:** поменяйте в `core.py` условие на противоположное
   (`==` на `!=`) и запустите ещё раз. Должно стать `False`. Верните как было.

Второй пункт — не формальность. Проверка, которая никогда не говорит `False`, ничего не
проверяет. Убедиться, что она умеет ловить ошибку, — обязательная часть любой проверки.

Это то же самое, что делает `check.py` с вашими `task`-ами: заранее записанный правильный
ответ и сравнение. Только теперь проверяльщик написали вы.

### Со звёздочкой — неудобная строка

Возьмите из своих **настоящих** данных строку, на которой непонятно, что должна сделать
программа: дата записана словами, поле пустое, «у дежурного» и «у дежурной» — это одно и то же?

Добавьте вторую проверку в тот же файл — только с этой строкой — и решите **с командой**,
какой ответ правильный. Если договориться не выходит — принесите вопрос в пятницу, это
отличный вопрос.

## Шаг 4. Понедельник: к заказчику с программой

**Для команды, которая едет в другую школу.** Остальные могут пропустить — или сделать
то же самое для своего заказчика в здании.

Файл `customer-visit.md` в репозитории команды, полстраницы:

1. **Какой вопрос решает программа** — одна строка, та же, что первая строка `project.py`.
2. **Что покажем** — одна команда запуска и то, что она напечатает. Показываем запуск,
   а не слайды и не рассказ.
3. **Три вопроса заказчику.** Не «вам нравится?», а про его работу:
   *«что вы делаете, когда…?»*, *«сколько раз за неделю…?»*, *«что было в последний раз,
   когда…?»*.
4. **Кто показывает** — тот, кто в команде выступал меньше всех.
5. **Кто записывает** — имя и роль заказчика, одна прямая цитата, одна цифра.

Через три недели никто не вспомнит, что именно сказал заказчик. Поэтому записываем в тот же день.

## Антипаттерны

| Что сдают | Что не так |
|---|---|
| `print` внутри `filter_items` | Функция снова и решает, и печатает. Проверить её можно только глазами — ради чего разделяли? |
| `expected` скопирован из вывода программы | Так проверка всегда скажет `True`, даже если программа ошибается |
| Проверка ни разу не показала `False` | Неизвестно, умеет ли она вообще ловить ошибку |
| В `check_core.py` все 20 строк данных | Нужно 3–4, ответ на которые можно выписать в уме. Большую проверку никто не пересчитает руками |
| `customer-visit.md`: «покажем приложение и спросим, нравится ли» | Заказчик вежливо скажет «да», и вы ничего не узнаете. Спрашивайте про его работу, а не про свою программу |
| Код, который не можете объяснить | Неважно, откуда он. Не объясните — не засчитано |
